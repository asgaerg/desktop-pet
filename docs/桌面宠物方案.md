# 桌面 AI 宠物：技术方案

> 目标：Windows 桌面端的 AI 宠物。常驻桌面、有动态立绘、可打字可语音实时对话、能看屏幕主动说话、活泼度可调；架构上为后续功能扩展留好插槽。

---

## 0. 一句话结论

**双进程架构**：`Electron` 负责"皮肤"（透明置顶窗、动态立绘、气泡对话、设置面板），`Python sidecar` 负责"大脑"（语音识别 / 语音合成 / 屏幕理解 / LLM 编排），两者用本机 `WebSocket` 通信。

理由：AI 生态（Whisper、OCR、本地 LLM、视觉模型）全在 Python，而动态立绘与桌面窗口特效的成熟方案全在 Web/Electron。强行统一成一种语言，两边都会被拖累。

## 2. 总体架构

```
┌──────────────────────────── Electron 主进程 ────────────────────────────┐
│  透明无边框置顶窗 · 点击穿透 · 拖拽 · 托盘 · 全局热键 · 多显示器定位      │
│                                                                        │
│  渲染进程（Web）                                                        │
│    · 动态立绘：PIXI + pixi-live2d-display（Live2D）或 three + VRM       │
│    · 表情/口型：由状态机的 emotion / mouth 参数驱动                     │
│    · 气泡 & 迷你输入框 & 设置面板（活泼度滑杆、人格、模型选择）          │
└───────────────────────────────┬────────────────────────────────────────┘
                                │ 本机 WebSocket（JSON 事件流 + 二进制音频）
┌───────────────────────────────┴──────── Python Sidecar（核心）──────────┐
│  Bus 事件总线（publish/subscribe，全模块唯一耦合点）                     │
│                                                                        │
│  ├─ InputGateway   ：打字文本 / 语音转写文本 统一入口                    │
│  ├─ AudioIn       ：麦克风 → VAD（silero-vad）→ 流式 ASR（faster-whisper）│
│  ├─ AudioOut      ：TTS 流式合成 → 分句播放 → 音素/包络送口型            │
│  ├─ VisionLoop    ：定时截屏 → 画面变化检测 → 去重 → 转描述/文字          │
│  ├─ Brain         ：人格 Prompt + 情绪状态 + 记忆检索 + LLM 流式生成      │
│  ├─ Autonomy      ：自主行为调度器（"什么时候自己开口"）                 │
│  ├─ Memory        ：短期上下文窗口 + 长期向量库 + 用户画像               │
│  └─ PluginHub     ：能力注册表，后续功能以插件形式挂载                   │
└────────────────────────────────────────────────────────────────────────┘
```

**唯一硬规则**：模块之间不直接互相调用，一切都过 Bus。这样加功能只需要"订阅事件 + 发布事件"，不动老代码。

## 3. 关键技术选型（含取舍）

### 3.1 动态立绘

**已定方案：序列帧动画。** 不用 Live2D，也不用 VRM。

| 方案 | 表现力 | 成本 | 授权 | 结论 |
|---|---|---|---|---|
| **序列帧 / 图集** | 中上，取决于画师 | 低：一张横向贴图 + 一份帧表 | **自绘则零风险** | ✅ **采用** |
| Live2D Cubism（PIXI + pixi-live2d-display） | 最好，眨眼/呼吸/口型/触摸现成 | 中：需 Cubism Core 运行时 | Cubism SDK 商用需授权，免费模型多限个人非商用 | ❌ 放弃（授权与复杂度不划算） |
| VRM（3D）+ three-vrm | 好，可换装 | 中高：引 WebGL 与 3D 管线 | 完全免费 | ❌ 放弃（本需求用不到 3D） |

**素材约定**（`apps/desktop/src/renderer/assets/avatar/<名字>/`）：

```jsonc
// avatar.json
{
  "image": "sheet.png",          // 横向排列的帧序列，帧号 = 从左到右下标
  "frameWidth": 256, "frameHeight": 256,
  "fps": 8,                      // 默认帧率
  "palette": { "body": "#ffb35c" },   // 缺素材时的程序化占位配色
  "animations": {
    "idle":    { "frames": [0,1,2,1], "fps": 6,  "loop": true  },
    "blink":   { "frames": [3,4],     "fps": 14, "loop": false },
    "talk":    { "frames": [5,6,7,6], "fps": 13, "loop": true  },
    "drag":    { "frames": [8],       "loop": true  },
    "sleep":   { "frames": [9,10],    "fps": 2.2, "loop": true },
    "happy":   { "frames": [11,12,11], "fps": 10, "loop": true },
    "curious": { "frames": [13,14],   "fps": 5,  "loop": true  }
  }
}
```

**为什么这个结构值得坚持**：状态机（`idle/blink/talk/drag/sleep`）与素材完全解耦。
换一套立绘（换画师、换画风、换成程序化绘制）只动素材与 manifest，播放逻辑一行不改。

**素材缺失时的兜底**：`sprite.js` 里内置了程序化绘制的占位宠物——会呼吸、会眨眼、
说话时嘴跟着动、困了冒 Z。这不是为了好看，而是为了**在没有任何美术资源时，
口型/情绪/状态机整条链路依然可被验证**。仓库里另有一份生成的 16 帧占位贴图
（`pnpm avatar` 重新生成），所以"贴图加载"这条真实路径今天就在跑，不是等美术到位才第一次踩坑。

口型同步：TTS 输出音频时给出**音量包络**，渲染端把它映射成嘴部开合高度即可。
拿不到音素也没关系，包络已经足够自然。协议里 `pet.mouth` 就是为此预留的。

### 3.2 语音识别（实时）

- **本地**：[`faster-whisper`](https://github.com/SYSTRAN/faster-whisper)（CTranslate2 后端）+ `silero-vad` 做端点检测。GPU 上 `small` 模型可近实时，中文够用。
- **云端**（低延迟、省显存）：火山/阿里/讯飞/OpenAI 流式 ASR，走 WebSocket 边说边出字。
- **推荐**：**双通道可切换**——默认本地（隐私、离线可用），设置里可切云端；接口抽象成 `ASREngine`，实现类互换即可。

### 3.3 语音合成（TTS）

- 本地：`GPT-SoVITS` / `edge-tts`（免费、质量意外地好、零显存）
- 云端：火山、MiniMax、ElevenLabs
- **关键**：必须**流式 + 分句**。LLM 一出第一句就送去合成并播放，感知延迟从 3~5s 降到 1s 内。这是体验的分水岭。

### 3.4 屏幕"看见"能力（本方案最容易翻车的部分，重点设计）

不要"每秒截屏问模型"，那样又贵又傻。分层做：

```
每 N 秒截屏（默认 20s，活泼度高时 8s）
   ↓
变化检测：感知哈希 / 直方图差异 → 与上次差异过小则整轮跳过（省钱 90%）
   ↓
理解层（三级，可配置）
   ├─ L1 文字层：本地 OCR（RapidOCR / PaddleOCR）→ 得到窗口标题 + 屏幕文字
   ├─ L2 语义层：本地小 LLM 或云端纯文本模型 → "用户在写代码/看视频/打游戏"
   └─ L3 视觉层：多模态模型（GPT-4o / Qwen-VL / 本地 Qwen2.5-VL）→ 真正"看懂画面"
   ↓
生成 Observation 事件 {场景, 摘要, 新鲜度, 隐私等级}
   ↓
Autonomy 决策器判断：值得开口吗？
```

**隐私与安全闸门（必做）**：内置窗口/关键词黑名单（密码框、银行、聊天软件、指定进程），命中即不截屏；截屏前可先只取窗口标题判断；提供"暂停看屏幕"热键与托盘开关。这条不做，用户迟早会删掉这个软件。

### 3.5 大脑（LLM 编排）

- 统一走 **OpenAI 兼容接口**（`base_url` + `model` 可配），这样 DeepSeek、通义、本地 llama.cpp / Ollama / vLLM 全部同一套代码。
- **必须流式**（SSE），配合 TTS 分句，首字响应 < 1s。
- 分层模型策略省钱：闲聊用便宜小模型，复杂问题/看图升级到大模型。

### 3.6 记忆

| 层 | 内容 | 实现 |
|---|---|---|
| 工作记忆 | 最近 20~50 轮 | 内存 + SQLite 落盘 |
| 长期记忆 | 用户偏好、重要事件 | 向量库（Chroma / LanceDB），对话后异步抽取写入 |
| 用户画像 | 称呼、作息、常做的事 | 定期由 LLM 归纳更新 |

## 4. 活泼度参数设计（核心创新点，别做成一个滑杆）

不要只有一个 `liveliness`，要拆成一组可解释参数，UI 上给一个总滑杆联动多个分项：

```yaml
# config/persona.yaml
activity:
  overall: 0.6            # 总活泼度（滑杆直接绑这个）
  # 以下由 overall 联动，也可手动覆盖
  idle_chatter_rate: 0.5  # 无输入时主动开口的频率
  screen_watch_prob: 0.4  # 看到屏幕变化时"忍不住评论"的概率
  reaction_latency: 1.2s  # 反应延迟（越低越"跳"）
  interrupt_prob: 0.15    # 主动打断/插话的倾向
  message_length: 0.5     # 啰嗦程度（短促 vs 长篇）
  emoji_sticker_rate: 0.3 # 表情/动作幅度
  quiet_hours: ["23:30-07:30"]  # 免打扰
  focus_guard: true       # 检测到全屏/会议/游戏时闭嘴
```

**实现方式**：`Autonomy` 是一个**带冷却的加权调度器**，每个 tick（如 5s）计算一次"开口意愿分"：

```
意愿 = overall × 场景权重(屏幕新鲜度/空闲时长/情绪) − 冷却惩罚 − 打扰惩罚
意愿 > 阈值  →  触发自主发言
```
参数全部热重载，改滑杆立刻生效，不用重启。

### 情绪状态机

三个维度 `精力 / 情绪(正负) / 亲近度`，随交互增减，影响：台词风格、立绘表情、动作频率、说话长度。用于防止"像个设定好的复读机"。


## 7. 实时交互的延迟预算（决定"像不像活的"）

| 环节 | 目标 | 手段 |
|---|---|---|
| 语音端点检测 | 300~500ms | silero-vad 动态阈值，允许插话打断 |
| ASR 出字 | < 500ms | 本地 small + 流式；或云端流式 |
| LLM 首 token | < 800ms | 流式 + 云端快模型 |
| TTS 首音频 | < 500ms | 分句流式合成，第一句就播 |
| 立绘口型响应 | < 100ms | 包络随音频帧推送 |
| **端到端（说完→它开口）** | **< 2s** | 以上叠加 |

超过 3s，用户就会觉得"这玩意儿卡"，宠物感立刻消失。**所以流式是硬要求，不是优化项。**

## 8. 分阶段实施路线

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0 骨架**（1~2天） | Electron 透明置顶窗 + Python WS 服务 + Bus + 消息 schema | 打字→宠物气泡回字，能拖动、能穿透 |
| **P1 立绘**（2~3天） | 接入 Live2D/VRM，眨眼呼吸 + 表情切换 + 口型 | 说话时嘴跟着动，有情绪表情 |
| **P2 大脑**（2~3天） | 人格 Prompt + 流式 LLM + 情绪状态机 + 短期记忆 | 对话自然，人格稳定不崩 |
| **P3 语音**（3~5天） | VAD + 流式 ASR + 流式 TTS + 打断 | 按住说话/免提，端到端 <2s |
| **P4 看屏幕**（3~5天） | 截屏 + 变化检测 + OCR/VLM + 隐私黑名单 | 切到写代码它会说"又在卷啊" |
| **P5 活泼度**（2天） | Autonomy 调度器 + 滑杆 + 情绪联动 + 免打扰 | 拉到 0 它闭嘴，拉到 1 它会主动搭话 |
| **P6 打磨**（持续） | 托盘、热键、开机自启、多屏、自动更新、装机包 | 能长期挂着不崩、不占满显存 |
| **P7 扩展** | 插件机制 + 更多能力 | 新增功能不动主循环 |

建议节奏：**P0~P2 先出一条"能用"的竖切**（文字 + 立绘 + 人格），确认手感对了再上语音和视觉。语音视觉是两个大坑，别一上来就啃。

## 10. 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| Live2D 授权 | 不能商用/分发 | 早期就定：自绘、买授权、或改用 VRM |
| 显存不足 | ASR + LLM + VLM 抢 8GB | ASR 常驻、VLM 按需加载卸载、对话走云端 |
| 截屏隐私 | 用户信任崩塌 | 黑名单 + 一键暂停 + 本地处理优先 + 明示 |
| 云端 API 成本 | 挂一天烧钱 | 变化检测去重、分层模型、本地兜底、日额度上限 |
| 模型冷启动卡顿 | 第一次说话等 5s | 启动时预热，模型常驻 |
| 一直说话很烦 | 用户卸载 | 免打扰时段、专注保护、"闭嘴 30 分钟"快捷指令 |
| 全屏游戏/会议时弹窗 | 严重打扰 | 检测全屏独占/摄像头占用，自动进入沉默模式 |

## 11. 已锁定的关键选择

| 决策项 | 结论 | 落地方式 |
|---|---|---|
| 大脑位置 | **混合** | ASR 本地常驻（faster-whisper small）；对话 LLM 走云端；视觉理解按需调云端多模态 |
| 立绘形式 | **序列帧动画** | 横向图集 + `avatar.json` 帧表；不用 Live2D / VRM，零授权风险、无 WebGL 依赖 |
| 首版范围 | **打字 + 看屏幕先行，语音后置** | P0~P2 出竖切，P3 语音单独作为阶段 |

由此确定的实施顺序：**P0 骨架 → P1 立绘 → P2 大脑 → P4 看屏幕 → P5 活泼度 → P3 语音 → P6 打磨 → P7 扩展**。

### 11.1 混合模式的具体分工

```
本地（常驻）：
  · faster-whisper small int8_float16   ≈1.0 GB 显存 —— 语音识别
  · silero-vad                          ≈0 GB     —— 端点检测（P3 才需要）
云端（按量）：
  · 对话 LLM（OpenAI 兼容接口，如 DeepSeek）—— 流式，首 token <800ms
  · 多模态 VLM —— 仅在变化检测判定"值得看"时调用，且截屏先降分辨率
```

**成本控制三件套**（决定这个软件能不能长期挂着）：
1. 画面感知哈希去重 —— 屏幕没变整轮不调用，省 ~90%；
2. 截图压缩到长边 768px 再送 VLM —— token 消耗降一个数量级；
3. 日额度上限 + 超限自动降级到本地 OCR 文本模式。

### 11.2 序列帧立绘的制作要点（取代原 Live2D 授权清单）

- [x] 授权风险：**自绘 / 委托绘制则完全没有授权问题**，这是放弃 Live2D 的主要收益；
- [ ] 帧率与帧数：`idle` 4~6 帧即可有呼吸感；`talk` 3~4 帧足够（口型靠包络缩放）；
      `blink` 2 帧；`sleep` 2 帧。**别一上来就画 30 帧**，收益极低而成本极高；
- [ ] 贴图尺寸：单帧 256×256 起步，横向排列。帧数 × 帧宽别超过 GPU 纹理上限
      （一般 8192），超过就要改多行图集——`sprite.js` 里已按行推导，多行无需改代码；
- [ ] 一致性问题：序列帧最大的坑是**帧间抖动**（轮廓/颜色轻微跳动）。修法是把所有帧
      画在同一张底稿上、只改动的部位单独分层导出，而不是每帧重画；
- [ ] 交付格式：PNG（带 alpha）+ 一份帧表。给画师的说明就是本文 3.1 的 `avatar.json`。

## 18. P2 已交付：长期记忆

### 18.1 零依赖怎么做检索

长期记忆的难点不是存储而是**检索**，而本机没有任何嵌入模型
（sentence-transformers / torch / onnxruntime 全无，下载权重也不现实）。
所以用经典的**哈希技巧**：

```
文本 → 按字符类型统一分词 → 四层特征 → 带符号哈希到 256 维 → L2 归一化
检索 → 余弦相似度 + 关键词提权
```

**四层特征**（权重从高到低）：整串归一化文本 → 整词 → 词内单字 → 字符 n-gram。
分层是调出来的：只用字符 2/3-gram 时，短查询几乎检索不到东西
（实测 "猫" vs "我们家的猫叫豆豆" 只有 0.24，"桌面宠物" 甚至是负数）。

**带符号哈希**是关键：不带符号时所有特征只做加法，任意两段文本的向量都会
互相靠近，相似度失去区分力。

**关键词提权**同样必需：查询"Rust 学得怎么样"里的"学得怎么样了"会在向量空间
贡献大量噪声，把真正的信号稀释掉（余弦仅 0.15，低于默认阈值 0.18）。
而"Rust 同时出现在查询与记忆里"本身是极强证据，所以单独计分。
实测把 5 条相关查询的召回从 2/5 提到 5/5，同时无关查询仍压在 0.1 以下。

### 18.2 三个"静默失效"的坑（都实测踩过）

| 现象 | 根因 | 教训 |
|---|---|---|
| `rust` 被截成 `rus` | 用 `re.sub(r"(...)(...)|(...)(...)", r"\1 \2", ...)` 时，未参与匹配的分支让拼接丢掉了尾字符 | 这种静默截断最难查（相似度只是变差、不报错）。改成逐字符扫描 |
| 去重对"我在学Rust"与"我在学 Rust"失效 | 空格位置不同导致分词不同（3 词 vs 6 词），特征集分叉，余弦掉到 0.63 | 归一化必须保证"相同语义 → 相同特征"，否则所有依赖它的逻辑都会漏 |
| 检索分数虚低 | 短查询的关键词信号被无关字词稀释 | 换个思路：与其压低阈值放进噪声，不如把强信号单独提权 |

### 18.3 隐私与容量

写入前有敏感度过滤：**密钥、密码、证件号、手机号一律不落盘**，
而且要过滤两次——用户原话进库前一次，模型提炼出的事实进库前再一次
（模型可能不听话地把密码抽出来）。

容量满时按 `重要度 + 使用次数×0.03 + 事实加成 + 时间衰减` 淘汰。
把"被检索过"算进去是刻意的：经常被想起来的记忆显然更重要，
而一次都没用过的长尾条目留着只是占地方。

记忆文件放在 `~/.desktop-pet/memory.jsonl`——**属于用户而不是项目目录**
（放仓库里既会被 git 带走，也会在换目录后"失忆"）。用 JSONL 是因为追加写入
不会因为崩溃毁掉整个库、可人工打开检查；损坏的行会被跳过而不是丢弃全部。

### 18.4 落盘才是"记住了"的唯一证明

一个很隐蔽的回归：记忆写进内存、检索正常、对话看起来完全正确——
但**没有任何地方调用 `save()`**。`save()` 存在却从未被调用，
直到重启才发现全丢了。

现在有三道保证，而且都有测试盯着：

| 时机 | 机制 |
|---|---|
| 抽到新事实时 | 立刻落盘（这些是最有价值的内容，崩溃不该丢） |
| 每 30 秒 | 定时落盘，但**仅在有待写内容时**才真的写文件 |
| 进程退出时 | `Gateway.shutdown()` 里强制落盘，这是最后的保证 |

测试会验证完整闭环：写入 → 落盘 → 新建实例模拟重启 → 读回 → 仍可检索。

### 18.5 记忆必须可见、可控

界面底部显示"记得 N 条（M 条事实）"，悬停能看到文件路径与各类统计，
旁边有「忘掉」按钮（二次确认，且真的从磁盘删除）。

这不是装饰：**记忆是看不见的东西，看不见用户既不会信任它，也不会想到去清理。**
把条数露出来、把清空入口放在手边，隐私控制权才算真的交回用户。

## 17. P3 已交付：语音链路

### 17.1 架构决定：音频 I/O 放在渲染层

本机**一个音频库都没有**（sounddevice / pyaudio / webrtcvad / silero 全无），
而 Electron 渲染层的 Web Audio API 原生就能采麦克风与播放。所以：

```
Electron 渲染层   采麦克风 PCM → 重采样 16kHz → 推给主进程；解码并播放宠物语音
      ↕ 二进制帧（不走 JSON：音频每秒 50 帧，base64 要白涨三分之一）
Python sidecar    端点检测 · 识别 · 合成 · 打断判定 · 状态机
```

收益是 Python 侧只处理 **PCM 字节**，纯标准库（`audioop`）就能算完 ——
于是语音里最容易出问题的部分（时序）可以用合成音频完整离线验证，
不必依赖任何麦克风。

### 17.2 用合成音频验证八件事

测试用例把 "静音 300ms / 语音 800ms" 这样的描述展开成 20ms 帧序列，
用正弦波当人声（能量与过零率都像浊音）、低幅噪声当环境底噪：

| 行为 | 断言 | 实测 |
|---|---|---|
| 静音不误触发 | 纯静音不产生语音判定 | 通过 |
| 环境噪声不误判 | 40 帧持续噪声不被当成说话 | 噪声底自适应到 0.0052 |
| 换气不误切 | 说 800ms + 停 200ms + 说 700ms | 只切出 **1 句** |
| 两句正确分开 | 说-停-说-停 | 切出 **2 句**（0.56s / 0.56s） |
| 短声响丢弃 | 60ms 响声 | **0 句** |
| 超长截断 | 3s 连续语音、上限 1s | 在 1s 处截断，标记 `max_length` |
| 插话打断 | 宠物说话时用户开口 | 发 `user.interrupt` + 停止播放 |
| 口型包络真实 | 响段 + 静段 | 0.42 → 0.00（不是随机数） |

第三条最关键：**换气被当成说完**是语音对话最典型的失败——句子被切碎，
回复必然答非所问。靠 `end_silence_ms`（500ms）+ 起说消抖（3 帧）解决。

### 17.3 几个刻意为之的取值

| 参数 | 值 | 为什么 |
|---|---|---|
| `end_silence_ms` | 500ms | 最影响体验的一个数。太小切碎句子，太大每句都多等 |
| `start_frames` | 3（60ms） | 防敲键盘、爆音这类瞬时噪声 |
| `barge_in_frames` | 5（100ms） | 判插话比判起说**更严格**，避免宠物自己的尾音把自己打断 |
| `min_speech_ms` | 250ms | 咳嗽、敲桌子不该触发识别（省一次调用） |
| `max_utterance_ms` | 30s | 保险丝，防缓冲区无限增长 |
| 浏览器降噪/自动增益 | **关闭** | 那些是给通话设计的，会把语音动态压平，反而更难判断"有没有在说话" |

### 17.4 两个实现细节值得单独说

**① 尾音必须剪掉。** 端点检测为了确认"真的说完了"必须多等 `end_silence_ms`，
如果把这 500ms 静音一起交给 ASR，Whisper 这类模型在长尾静音下更容易产生
幻觉文字，时长统计也会系统性偏长。所以 `Endpointer` 会记录最后一段语音
结束时的缓冲位置，收尾时裁剪到那里。

**② 音频配对要靠序号。** 一个 WebSocket 上文本与二进制是两条独立通道，
sidecar 先发 `voice.audio`（JSON，带 index）再发二进制帧，前端必须按**序号**
配对，不能靠"第几个到"去猜。这个坑在实现时差点踩进去。

### 17.5 引擎降级：语音不该是启动的硬门槛

`asr.provider` 与 `tts.provider` 缺依赖或缺密钥时**一律降级到 mock 并说明原因**，
绝不让宠物起不来：

| 情况 | 行为 |
|---|---|
| `asr.provider=openai` 但没密钥 | 降级 mock，提示"缺少密钥" |
| `asr.provider=local` 但没装 faster-whisper | 降级 mock，提示"需要 faster-whisper" |
| `tts.provider=none` | 不出声，只显示文字，提示"暂不出声" |

默认配置就是 `asr=mock` + `tts=none`：**开箱即跑通链路、不花钱、也不假装能听懂你**。

## 15. P4 已交付：屏幕感知的采集与分析层

### 15.1 为什么拆成两层

```
采集层（PillowCapturer，依赖平台）  抓像素 → 8x8 灰度网格 → 顺带取窗口标题
      ↓
分析层（vision.py 纯函数，零平台依赖）  隐私闸门 → 变化检测 → 新鲜度评分
      ↓
两个通道分开走：
  · 信号通道 novelty    → 调度器决定"要不要开口"
  · 内容通道 窗口标题    → 大脑决定"说什么"
```

拆分的收益是**可验证性**：整个方案里真正省钱、也真正决定体验的是分析层
（"屏幕没变就整轮跳过"省掉约 90% 模型调用），而它恰好不需要真实屏幕就能测。
于是 P4 的核心逻辑在没有 GUI 的环境里被完整验证，采集实现退化成一层薄适配器。

### 15.2 变化检测：全套方案里最省钱的一个组件

用 64 位感知哈希（8×8 灰度网格 vs 全图均值），汉明距离低于阈值即判定"没变化"、
整轮跳过。映射刻意做成阶跃而非线性：距离一到阈值就迅速拉升到高分并饱和，
因为用户期望的是"它注意到我切窗口了"，而不是"它按比例注意到"。

实测（合成帧）：21 帧里跳过 20 帧，**省 91%**。

真实屏幕实测还暴露了一个参数问题：看视频/滚代码时，1.5 秒内画面变化仍会给出
距离 8（阈值 5），于是连续判定为"有变化"。所以阈值做成了可配置项
（`vision.change_threshold`，默认 5，实测 8~12 更安静）。

### 15.3 隐私：硬约束，排在一切分析之前

命中黑名单的窗口**连哈希都不算**，帧直接丢弃。有两个容易写错的点：

1. **被拦下时不能刷新新鲜度。** 否则你打开密码管理器反而会让宠物更想开口 ——
   逻辑上完全反了。有专门的测试盯着这条。
2. **默认必须带规则。** 用户没配隐私段时退回内置的 16 条保守规则，
   绝不"没配 = 没有保护"。也有测试盯着。

### 15.4 感知循环的两个行为约定

- **没新东西时报告"陈旧"而不是"未知"。** 返回 None 会让调度器把
  `require_observation` 判为不满足；返回一个大秒数才表达"我看过，但没什么新东西"。
- **无变化时把抓取间隔逐步拉长**（最多 4 倍），一旦有变化立刻回到基准间隔。
  大部分时间用户在做同一件事，高频截屏纯属浪费电和 CPU。

### 15.5 可验证性：真实屏幕也能自检

`python -m pet --vision-test` 会对着真实屏幕跑几轮，打印采集器可用性、
帧尺寸与指纹、亮度跨度、窗口标题、隐私规则命中情况、以及跳过比例。
在这台机器上的实测输出：

```
采集器：pillow，可用
尺寸：1920x1080   指纹：0x00efffe7e7f2ff78   亮度跨度：179
窗口标题：NVIDIA GeForce Overlay DT | 桌面宠物实时聊天方案 — DeepSeek Harness | …
清洗检查：标题干净
隐私规则：16 条；"我的密码 - Chrome" → 拦下（title:密码）
```

这里也修掉一个真实缺陷：窗口标题里常混零宽字符（U+200B 等，Electron 应用标题栏
尤其常见），既会污染提示词，也会让 GBK 控制台直接抛 UnicodeEncodeError 把日志搞崩。
现在在采集层就清洗掉。

### 15.6 观察内容真的进了提示词

如果只是发个 `vision.observation` 事件却不让模型看到，那感知就是个装饰。
所以 `LLMRequest` 多了一个 `context_hint` 字段（与 `system` 分开，便于排查
"它为什么这么说"），Gateway 会把观察内容组织成线索塞进去，并**按可信度分两种措辞**：

- 只有窗口标题时：只给线索，并明确要求"不要假装看到了标题以外的具体内容"
  ——标题常是"未命名 - 编辑器"这种废话，当结论喂给模型会让它过度演绎；
- 有画面描述（视觉模型给的）时：可以直接引用，但仍要求"不要补充描述里没有的细节"。

自检里有一条断言验证 mock 的自主发言确实围绕窗口标题展开。

## 16. P4 内容层：三级抽取链

### 16.1 三级成本阶梯

| 级别 | 实现 | 成本 | 能看懂什么 |
|---|---|---|---|
| L1 | `WindowTitleExtractor` | 零（采集时顺带拿到） | 用户在用什么程序；有时足够 |
| L2 | `OcrExtractor` | 免费、离线 | 画面上的文字（免费但慢，需装 tesseract） |
| L3 | `OpenAIVisionExtractor` | 按量计费 | 真看懂画面：在写代码 / 在看视频 / 报错了 |

链路是 **按成本从低到高依次尝试，凑够内容就停**（`min_chars_before_next`）。
默认顺序 `title → ocr → vlm` 刻意保守：**默认状态下完全不花钱**。

### 16.2 成本控制的两个实测数字

"省 90%"这个说法现在有测试盯着，不再是一句宣传：

| 手段 | 实测效果 |
|---|---|
| 变化检测（画面没变整轮跳过） | 100 帧里只调用视觉模型约 10 次，**省 90%** |
| 截图压缩到长边 768px | token 量级从约 **2765 降到约 440**（一个数量级） |

第二项在真实屏幕上量的：`python -m pet --vision-test` 会打印原始尺寸、
编码后大小与 token 量级估算。

### 16.3 为什么抽取要放线程池且有超时

OCR 可能几百毫秒，视觉模型可能几秒。如果同步抽取，感知循环会被拖住，
连带把自主调度也卡住——表现为"宠物明明看到屏幕变了却不说话"。

所以 `VisionLoop.astep()` 把抽取丢进 `asyncio.to_thread` 并加超时：
超时就放弃这一帧的内容，**观测本身照样有效**（窗口标题还在）。
变化事件在抽取之前就发出去，宠物反应快；内容算好后再补进观测里。

### 16.4 实现里抓到的两个真实缺陷

| 现象 | 根因 | 教训 |
|---|---|---|
| 视觉模型永远不触发，报"没有可发送的图像数据" | 抽取器读的是 `frame.jpeg`，而 `Frame` 的字段叫 `image`；`getattr(..., None)` 把属性名不一致掩盖成了"没数据" | 属性名不一致时**不要用 getattr 兜底**，让它直接 AttributeError 更好 |
| 配置里写了 `vision.api_key_env`，但改了没用 | 代码没读这个字段 | 文档承诺了就必须实现；这类"配了没反应"最难排查 |

第一个缺陷特别典型：如果没有针对"图片是否真的被发出"的断言，
它会一直静默失效到用户第一次配上真实视觉模型时才暴露。

## 13. P5 已交付：活泼度自主调度器

### 13.1 为什么不能只做一个滑杆

最初的设计里"活泼度"只是一个 `overall` 参数。但那解决不了真正的问题：
**宠物什么时候该自己开口？** 滑杆要能拖动，就必须有一条确定的曲线把
"活泼度"映射到"开口频率"，而且这条曲线要能被解释。

于是拆成两件事：

| 配置段 | 回答的问题 | 例子 |
|---|---|---|
| `activity` | 说话**什么风格** | 回复长短、要不要用语气词、表情幅度 |
| `autonomy` | **什么时候自己开口** | 阈值、冷却、空闲多久才搭话、静音时段 |

### 13.2 意愿评分模型

```
意愿 = 0.9×观察新鲜度×screen_watch_prob
     + 0.75×空闲程度×idle_chatter_rate
     + 0.20×亲近度
     ────────────────────────────────  × (1 − 冷却惩罚)

空闲程度 = clamp01((安静秒数 − idle_after_s) / (idle_full_s − idle_after_s))
观察新鲜度 = clamp01(1 − 距上次屏幕变化秒数 / observation_decay_s)
冷却惩罚 = max(1 − 距上次交互/45s, 1 − 距上次开口/60s)   [截断到 0~1]

阈值 = 1.05 + (0.22 − 1.05) × 活泼度
```

**抑制门优先于意愿**，命中任一条件直接返回"不说"：

| 顺序 | 条件 | 说明 |
|---|---|---|
| 1 | `autonomy.enabled=false` | 总开关（只拦自动行为，见下） |
| 2 | `autonomy.muted=true` | 用户免打扰，由托盘/界面切换，走配置热更新 |
| 3 | `focus_guard` | 检测到全屏/会议（P4 置位） |
| 4 | `quiet_hours` | 静音时段，支持跨零点与限定星期 |

### 13.3 三个刻意的设计决定

**① 决策里没有随机数。** 用户拖滑杆时行为必须可预期。想要"偶尔安静一下"的
自然感，调的是阈值曲线与冷却时长，不是掷骰子——否则参数调优无从下手。

**② `enabled=false` 不拦手动触发。** 关掉的是"自动找机会说话"，
而"用户戳它一下想听它说"是完全不同的诉求。混在一起会让用户觉得开关坏了。
免打扰/静音时段/专注保护则对两者一律生效。

**③ 启动瞬间不算冷却中。** 早期实现里 `last_interaction_at = now`，
导致宠物开机后 45 秒内对任何屏幕变化都毫无反应——"刚打开是死的"。
现在把"上次交互"往前推一个冷却时长，等价于"已经安静够了"。

### 13.4 可测试性是设计出来的，不是补上去的

自主行为的验证难点全在时间上：等 15 分钟看它说不说话，等于没有测试。
因此调度器的**单调时钟与墙钟是分开注入的**：

- 单调时钟用来算时长（冷却、空闲）；
- 墙钟用来判断静音时段（几点几分、星期几）。

自检里用假时钟把一天压缩到毫秒级，于是有了这些确定性断言：
阈值随活泼度单调下降、四条抑制路径优先于意愿、冷却不被活泼度覆盖、
观察新鲜度衰减、亲近度不足以单独越线、启动即无冷却。

外加一条**真实 WebSocket 端到端**：`user.poke → 自主发言`
（断言 `priority=low`、历史里没有用户消息、免打扰期间真的被拦下且不产生对话轮次）。

### 13.5 自动化测试抓到的真实缺陷

写测试的过程中，下面这些都不是"测试写错了"，而是**实现本身有问题**：

| 现象 | 真正原因 |
|---|---|
| 免打扰期间"戳一下"仍会说话 | 手动路径绕过了抑制门 |
| 免打扰只在界面生效 | 前端只屏蔽了显示，sidecar 仍在生成并推送——既费 token 又名不副实。现在落成 `autonomy.muted` 配置项 |
| 宠物开机 45 秒内绝不开口 | 启动即处于冷却中 |
| `Config()` 缺 `autonomy` 段导致 KeyError | 默认 root 漏了一段，只有 `_validate` 会补 |

## 14. 渲染层的一个隐蔽失败（值得单独记）

`renderer/sprite.js` 早期写着 `export interface AvatarManifest` —— 这是
**TypeScript 语法**。浏览器解析 ES 模块时直接抛 SyntaxError，整个模块不执行，
**立绘在实际运行中从未加载过**。

可怕的地方在于它有多安静：

- Python 侧 14 项自检全绿（协议、流式、热更新都真的在工作）；
- 主进程构建成功、日志正常；
- 唯一线索是 devtools 控制台里一行 SyntaxError，而沙箱里根本起不了 GUI。

**教训**：一个进程的测试全绿，不能推断另一个进程是好的。渲染层需要自己的门禁。
于是加了 `tools/check-renderer.mjs`（`pnpm build` 会自动跑）：对 `renderer/`
下每个 `.js` 做纯语法编译，并单独识别"疑似混入 TypeScript 语法"的情况。
已用回归探针验证过它确实能拦住当初那个 bug。

同一轮的连锁影响：`sprite.js` 现在改名为 `sprite.ts`，由 esbuild 独立打包成
`renderer/sprite.js`（浏览器用的合法 ESM）。渲染层的 TS 源与运行产物从此分开。

### 14.1 后续扩成"契约检查"：又抓到两个同类问题

只做语法检查是不够的。后来把渲染层与 DOM / preload 的契约也纳入门禁时，
立刻抓到两个**语法完全正确、却会让脚本挂掉**的缺陷：

| 缺陷 | 后果 |
|---|---|
| `pet.on('voice.state')` 的通道不在 preload 白名单里 | preload 的 `on()` 会**抛异常**，而这两行在模块顶层 —— **整个 app.js 不执行**，等于界面全废 |
| `els.hint` 没在 `els` 对象里定义 | `renderAutonomy()` 一跑就 TypeError |

它们的共同点：`node --check` 通过、esbuild 打包正常、Python 侧 56 项自检全绿，
**从外部完全看不出问题**。顶层 `pet.on` 抛错尤其致命——不是某个功能失效，
而是整个渲染层脚本都不跑了。

现在 `pnpm build` 会自动检查五件事，每一条都对应一类真实缺陷：

| 检查项 | 防的是什么 |
|---|---|
| 元素 id 引用都在 index.html 里存在 | `$('hint')` 取到 null，随后 `.textContent` 报错 |
| 订阅通道都在 preload 白名单内 | 顶层抛错导致整个脚本不执行 |
| 调用的 `pet.*` 方法都已暴露 | 调了个 preload 没实现的方法 |
| `els.*` 属性都已定义 | 属性名拼错 |
| 渲染层文件无 UTF-8 BOM | 见下 |

**BOM 那条也是踩出来的**：修上面两个 bug 时我用 PowerShell 重写了源文件，
而 PowerShell 5.1 的 `Set-Content -Encoding UTF8` **默认会加 BOM**。
BOM 在 ESM 加载器里的处理因实现而异，编辑器里又完全看不出来 ——
正好属于同一类"看不见的致命问题"，所以一并纳入。

两道回归探针验证过门禁真的能拦住它们：把文件改回坏的状态，门禁确实 FAIL。

### 14.2 运行时测试：在假 DOM 里真的把界面跑起来

静态检查只能保证"能加载、名字对得上"，抓不到**逻辑是错的**。
所以又加了一个运行时测试台（`test:renderer`，53 项）：

用最小假 DOM + 假 canvas 上下文 + 假 pet API，把**真实的 `app.js` 与 `sprite.js`
跑起来**，然后推动协议事件、断言真实状态。不引 jsdom——需要打桩的 API 很少，
自己写反而更清楚、也更快（整套约 600 行，零依赖）。

它能验证的东西，静态检查一个都做不到：

| 类别 | 具体断言 |
|---|---|
| 流式对话 | 气泡累积成完整句子、思考态出现与消失、结束后移除流式标记 |
| **串台保护** | 迟到/错配的 `say.delta` 被丢弃（否则两句回复会混在一起） |
| 立绘状态机 | 素材真的加载（`mode === 'sprite'`）、帧真的在推进、发言切 `talk`、结束后回 `idle`、`blink` 播完自动回 `idle`、低精力进 `sleep` 并恢复 |
| 口型 | 说话时被驱动到合法非零值、不说话时归零 |
| 交互 | 输入去空白、空输入不发送、滑杆回显、免打扰、Esc 中断 |
| 状态显示 | 语音状态灯、记忆条数与清空、自主行为原因翻译成中文 |

**为此给 `SpritePlayer` 加了一个只读的 `debug` 快照**（`state` / `frame` / `mouth` /
`tick` 等）。这不是调试残留：这个播放器的逻辑无法目视验证，测试必须能读到真实状态；
它在 devtools 里排查问题时也很好用。只暴露读取、没有写入口，不会成为绕过状态机的后门。

### 14.3 做这个测试台踩到的三个坑（都很典型）

| 现象 | 根因 |
|---|---|
| 测试挂死、**什么都不打印** | 假定时器让 Node 事件循环永不退出，管道下的输出被缓冲住。表现成"无输出挂死"，看不出任何线索 |
| 用 loader hook 注册失败 | `module.register()` 需要 Node 20.6+，而 npm 脚本走 PATH 里的 node（本机 v14）。改成"拼接文件后整体求值"，不依赖任何 loader 特性 |
| 图片永远加载不完 | 假 `Image` 用 `setTimeout` 触发 `onload`，而全局 `setTimeout` 已被换成假实现（只在显式 flush 时触发）。真实异步必须用真定时器 |

还踩了一个测试自身的坑：装了假定时器之后，`await new Promise(r => setTimeout(r, 20))`
永远等不到回调 —— 测试自己要等待时必须用真定时器。

这三个坑都不在"被测代码"里，而在"测试环境"里。它们的共同教训是：
**测试台本身也是代码，也会有 bug，而且它的 bug 会伪装成被测代码的问题**
（比如"立绘没加载"其实是假 Image 没触发 onload）。

### 14.4 Node 版本

`test:renderer` 与 `test:main` 都会先检查 Node 版本并在不满足时给出明确提示。
本机 PATH 里的 node 是 **v14.15.0**，而 Electron 32 与这些工具都要求 Node 18+；
版本不够时的默认表现是一堆不知所云的语法错误，明确说一句能省掉不少时间。

### 14.5 主进程测试：抓到两个真 bug

主进程里有三块逻辑**从未被执行过**，而它们并不简单。补上测试后立刻抓到一个真 bug、
并在写测试的过程中又发现自己引入的一个：

| 缺陷 | 后果 | 怎么发现的 |
|---|---|---|
| `petSocket.ts` 引用了从未定义的 `OP_BINARY` | 收到**任何二进制帧**都抛 `ReferenceError` —— 语音音频完全收不到 | 测试里让服务端发一条二进制帧，立刻崩 |
| `audioPairer` 在元信息先到时序号错位 | 元信息（index=1）先到、二进制帧随后被记成 2，两边永远配不上对，**语音静默丢失** | 测试专门覆盖"元信息先到"这个顺序 |

第一个特别典型：`OP_BINARY` 只在"真的收到二进制帧"时才被求值，而本项目默认不出声
（`tts.provider=none`），所以在受限环境里**永远跑不到那一行**。它躲过了语法检查、
契约检查、以及所有 Python 侧的测试。

**这正说明"没被执行的代码等于没有代码"。** 测试用真 socket 起一个最小服务端，
按各种切分方式喂字节（包括跨 TCP 分片），才把这类问题逼出来。

### 14.6 写测试时的经验：测试台自己也会错

这一轮和上一轮的测试台一共踩了六七个坑，全部**不在被测代码里**，而在测试环境里：

| 现象 | 根因 |
|---|---|
| 挂死且无任何输出 | 假定时器让事件循环不退出，管道下输出被缓冲 |
| `module.register is not a function` | 该 API 需要 Node 20.6+，而 npm 走 PATH 里的 Node 14 |
| 图片永远加载不完 | 假 `Image` 用 `setTimeout` 触发 `onload`，而它已被换成假实现 |
| `await sleep()` 永不返回 | 装了假定时器后用真 `setTimeout` 才能睡着 |
| 子进程 `EPERM/EINVAL` | 本环境禁止带管道的子进程，所以测试不能现场调 esbuild |
| `.js` 被当成 ESM | 包内是 `"type": "module"`，CommonJS 产物必须用 `.cjs` |

**而且测试台的 bug 会伪装成被测代码的问题** —— 比如"立绘没加载"其实是假 Image
没触发 `onload`。所以断言失败时，先怀疑测试环境，再怀疑被测代码。

还修了几处**断言本身写错**的情况（它们都在"假装测试"）：
用不存在的路径测"显式指定优先"、用还在窗口内的时间测"窗口外清理"、
以及只取最后一次返回值导致断言恒为空。这类测试比没有测试更糟 —— 它们给人虚假的安全感。

## 20. 跨进程联调：唯一能发现"两侧各自自洽但不匹配"的手段

前面所有测试都是"某一端 + 打桩的另一端"。这留下一个结构性盲区：
**Python 与 TS 可以各自完全正确，却彼此不匹配。** 例如字段名差一个字、
枚举值不同、某条消息实际上从没被发出去 —— 两侧的测试都会通过。

所以补了一条真正跨进程的测试（`test:e2e`，34 项）：

```
拉起真实 Python sidecar（子进程）
      ↓ 真实 TCP + 手写 WebSocket 帧
真实 petSocket.ts 客户端
      ↓ 真实 parseMessage() 解析
逐条校验：字段、时序、内容、边界行为
```

它跑通的检查包括（全部真实字节往返）：

| 类别 | 验证内容 |
|---|---|
| 握手 | `ready` 携带全部五个子系统状态（人格 / 活泼度 / 调度器 / 语音 / 记忆） |
| 流式对话 | 增量**拼起来与最终文本完全一致**、同一发言 id 一致、真流式（非一次吐完） |
| 配置热更新 | 设定值生效、**越界值被夹取后回报** |
| 健壮性 | 非法输入得到可读错误、**被拒之后连接仍可用** |
| 自主行为 | 戳一下会主动说话、标记为低优先级、免打扰真的拦得住、解除后恢复 |
| 隐私 | 记忆清空回执与归零 |
| **语音整链** | 推静音不误触发识别；推正弦波"说话"能触发识别与回复 |
| 二进制通道 | 音频帧走二进制、客户端掩码正确 |

**"流式增量拼起来与最终文本一致"这条最值得说**：它是前端显示正确性的基础。
如果 Python 的增量与最终文本对不上，界面就会出现"说着说着突然变样"或重复，
而两边各自的测试都不会发现。

### 20.1 顺带修正的一处设计问题

写协议一致性检查时发现：前端订阅了 `voice.state` / `voice.audio` 两个
**以协议类型名命名的 IPC 通道**。那等于在主进程里按类型名又分了一次发，
与协议列表失去同步时就静默失效，而且让"订阅通道必须在白名单里"这条规则难以解释。

现在统一为：**除音频二进制体外，所有下行消息一律走 `pet:message`**。
只有音频本体走独立通道（它不能塞进 JSON）。

顺带发现 `protocol.json`（宣称的单一来源）**落后于实现**：
`voice.control` 与 `memory.clear` 在 TS 类型和 Python 白名单里都有，它这里没有。
一致性检查把这类"文档落后于代码"也纳入了断言范围。
