# AI 陪玩设计（2026-10-18 讨论稿）

> 用户问：「如果要实现 AI 陪用户打游戏，你觉得要怎么实现」。
>
> 这份是**设计讨论稿**，不是已实现功能。里面每个阶段都标了"能不能现在就做"。

---

## 一、先分清「陪玩」的三种形态（成本差 10 倍以上）

| 形态 | AI 做什么 | 能玩的游戏 | 风险 | 工作量 |
|---|---|---|---|---|
| **A. 陪聊解说** | 看画面、吐槽、提醒、记战绩 | 任何游戏 | 无（只读屏幕） | 小 ✅ 现在就能做 |
| **B. 副驾（co-pilot）** | 看画面 + 算数据 + 主动提示（"左边有人""这个 Boss 弱火"） | 大多数游戏 | 低（不操作） | 中 |
| **C. 真一起玩** | 自己操作角色，和你组队 | **只有三类**：官方 API / 模组 / 回合制 | 高（外挂红线） | 大 |

**我的建议：先做 A，再做 B，C 只挑"能合法操作"的那几款。**

理由很直接：**操控是最贵也最容易翻车的部分**，而"有人在旁边看着你打、记得你上次卡在哪、
该提醒的时候提醒"已经能提供 80% 的陪伴感。

---

## 二、C 为什么只能挑三类游戏（重要，先说清）

```
① 官方 API / 机器人协议
      Minecraft（Mineflayer）、Factorio、部分 MMO 的官方插件
      -> AI 通过 API 操作，合法、稳定、可测

② 模组 / 本地脚本
      星露谷（SMAPI）、RimWorld、部分像素游戏
      -> 只要有 mod 能读状态/下指令，就能接

③ 回合制 / 棋牌
      本质是"状态 + 合法动作集合"，LLM 直接能下
      -> 自己实现游戏更简单（不用接别人的）
```

**不做的：**

```
· 读游戏内存 / 改内存        -> 反作弊直接封号
· 注入 DLL / hook 渲染        -> 同上
· 通用"看屏幕然后发键鼠"       -> 延迟、误操作、被判宏，且几乎不可能稳定
  （唯一例外：如果你明确只玩单机、且接受"它可能点错"）
```

> 一句话：**"AI 操作角色"不是技术问题，是"合不合法"的问题。**
> 所以 C 的路线必须先选游戏，再谈实现。

## 三、架构（A/B 形态，能复用现有代码）

```
┌──────────────────────────────────────────────────────────────┐
│ 感知层                                                        │
│   截屏（已有 Ctrl+Alt+S + 定时视觉）                            │
│   差帧检测：只把"画面变了"的帧往后送（省 90% 的调用）            │
│   可选：本地 OCR / 小检测模型（onnx，2 秒内出结果）              │
└──────────────────────┬───────────────────────────────────────┘
                       ↓  结构化"游戏状态"
┌──────────────────────────────────────────────────────────────┐
│ 状态层（关键：不要每帧都喂给大模型）                            │
│   { game: 名称, scene: 战斗/菜单/地图, hp: 30%,                   │
│     events: ["Boss 出现", "血量低于 30%"], 上次提示: ... }      │
└──────────────────────┬───────────────────────────────────────┘
                       ↓
┌──────────────────────────────────────────────────────────────┐
│ 决策层                                                        │
│   规则优先（血低于 30% 一定提醒），LLM 只做"怎么说"             │
│   冷却：同一个提示 2 分钟内不重复说                              │
│   记忆：这场战绩、你卡过的点 -> 写进 memory（已有的记忆系统）      │
└──────────────────────┬───────────────────────────────────────┘
                       ↓
┌──────────────────────────────────────────────────────────────┐
│ 表达层                                                        │
│   气泡 / 语音（已有 TTS）/ 状态栏显示「陪你打游戏中」             │
│   C 形态再加一层：动作执行器（API 调用 / 键鼠）                  │
└──────────────────────────────────────────────────────────────┘
```

**和现有模块的对接点**（都是已经有的东西）：

```
modules.game      新模块开关（阶段一那套注册表直接加一行）
events.coop_game  已有事件定义（needs=("coop_game",)），现在 dormant
tools.game_*      function calling 加工具：game_state / game_hint / game_log
status 状态栏      已有，加一个"陪玩中"状态
memory            战绩、卡关点、你的偏好，本来就在记
```

## 四、延迟预算（这是能不能做成"实时"的关键）

| 方案 | 单次耗时 | 能不能实时 |
|---|---|---|
| 云端视觉模型看一帧（现在这套） | 12~18 秒 | ❌ 只能"每隔几分钟看一眼" |
| 差帧 + 只在关键事件时看 | 12~18 秒 / 事件 | ⚠️ 战术提示来不及，只能事后说 |
| 本地小模型（yolo/ocr，onnx） | 0.3~2 秒 | ✅ 能做"血低了""有人来了" |
| 游戏 API 读状态（C 形态） | <10 ms | ✅ 完美 |

> **结论**：想要"实时提醒"，必须走 ①本地小模型 或 ②游戏 API。
> 纯云端视觉只适合"事后点评"和"每 3~5 分钟看一眼"。

## 五、分阶段落地

### P0 · 陪聊解说（现在就能做，不用新依赖）

```
· 复现有能力：定时（3~5 分钟）看一眼屏幕 -> 说一句
· 加一条"游戏模式"：开启后视觉频率提高、发言更短更像"旁边的人"
· 战绩记进 memory（"上次打这个 Boss 死了 3 次"）
验收：你打游戏时它会自己说"这关你上次卡在第二个机关"
```

### P1 · 副驾（需要本地小模型或游戏日志）

```
· 本地 OCR 读血条/弹药/小地图（onnx，2 秒级）
· 规则引擎：血 <30% / 弹尽 / 死亡 -> 触发提醒（带冷却）
· LLM 只负责"怎么说"，不负责"看到什么"
验收：你血快见底时它开口提醒，且不重复啰嗦
```

### P2 · 真一起玩（挑一款，先做 Minecraft）

```
· Mineflayer（Node/Python 都有）让 AI 有自己的角色
· 它通过 tools 暴露：gather / follow / build / mine
· 它能"看见"你的位置，跟你走、帮你挖矿、提醒怪
· 因为是官方协议，不会被判外挂
验收：它能在服务器里跟着你走、听到"帮我挖点石头"就去挖
```

### P3 · 回合制小游戏（自己写一个最省事）

```
· 五子棋 / 21 点 / 猜词：状态 + 合法动作，LLM 直接下
· 好处：完全可控，能验证"AI 决策"这条链，不用碰任何外部游戏
验收：能跟你下完一整局，且会记"上次你赢了"
```

## 六、几个容易翻车的点（提前写下来）

```
① 别每帧都调云端视觉：一次 12~18 秒、还花钱。差帧 + 事件触发是必须的
② 别让 LLM 决定"看到什么"：它会把"血条 30%"读成"血量充足"。
   感知用确定性代码（OCR/检测），LLM 只决定语气
③ 提示要带冷却和去重：否则"小心！""小心！""小心！"会毁掉体验
④ 陪玩时要降低主动搭话频率：你正在打，它突然聊人生会很烦
   -> 走 modules.autonomy 的静音/降频，不要新写一套
⑤ C 形态一定先确认游戏条款：Minecraft 服务器要问服主、单人档随便
```

## 七、如果让我现在就动手，第一步做哪个

**做 P0 的"游戏模式"** —— 它不需要任何新依赖，全部复用现有代码：

```
1. modules 加 game（开关 + 状态）+ persona.yaml 一行
2. providers.game: { mode: 'commentary', screenshot_interval_s: 180 }
3. 检测到"游戏模式开"就：
   · 视觉频率从 10 分钟提到 3 分钟
   · 主动发言改成"短句点评"（加一条 prompt 规则）
   · 战绩写进 memory
4. 状态栏显示「陪你打游戏中」
```

大约半天工作量，而且不碰任何危险操作。做完之后你打一晚，就知道
"AI 陪玩"到底有没有用 —— 再决定要不要往 P1/P2 投入。

## 八、帧级实时可行吗（延迟预算，2026-10-18 补）

用户追问：「如果按照每帧识别，不变化不截图屏幕，这样能实时反应吗？
我是说单机游戏让 ai 玩，或者和 ai 玩不联网的联机游戏。」

### 8.1 先拆开：一帧要花的时间花在哪

| 环节 | 耗时（RTX 2070 / 本机实测或估算） | 能不能省 |
|---|---|---|
| 截屏（DXGI Desktop Duplication / BitBlt） | 5~15 ms | 省不了，这是下限 |
| 降采样 + 差帧比较（缩到 1/8，比哈希） | 1~3 ms | 已经很快，值得做 |
| **看懂画面（模型）** | **云端 12~18 s / 本地 7B VLM 0.3~1 s / 本地检测模型 10~40 ms** | **这才是瓶颈** |
| 决策（规则 / 小网络 / LLM） | 规则 <1 ms / LLM 0.3~3 s | 规则快，LLM 慢 |
| 动作注入（SendInput / XTest） | 1~5 ms | 省不了 |
| 屏幕回显（下一帧） | 1 帧 = 16.7 ms @60Hz | 物理下限 |

**结论：截屏 + 差帧一共 6~18 ms，完全够实时。瓶颈 100% 在"看懂画面"那一步。**

### 8.2 四种"看"的方案，闭环频率差 1000 倍

| 方案 | 单帧耗时 | 闭环频率 | 能玩什么 |
|---|---|---|---|
| 云端视觉（现在这套） | 12~18 s | 0.06 Hz | 回合制、事后解说 |
| 本地 7B VLM（量化，如 Qwen2.5-VL-7B） | 0.3~1 s | 1~3 Hz | 卡牌、战棋、慢节奏 RPG |
| **本地小检测模型 + 规则**（YOLO/OCR，onnx） | **20~70 ms** | **15~50 Hz** | **动作游戏（但要训练）** |
| 游戏 API / 读内存 | **<10 ms** | 100 Hz+ | 动作游戏（最稳） |

### 8.3 「不变化不截图」能省什么、不能省什么

```
能省：GPU 占用、云端调用费用、模型推理次数（画面静止时）
不能省：延迟本身 —— 差帧是在"看懂画面"之前做的，省的是那一步的调用，不是它的耗时
而且动作游戏画面几乎一直在变（角色呼吸、粒子、UI 动画、摄像机微动），
按整帧哈希判断"没变"会一直为真 -> 根本省不下来
```

**更有效的省法：只看 ROI（兴趣区域）**

```
血条区域 200x20 像素 + 小地图 200x200 + 准星附近 400x400
-> 每帧只对这些区域做检测，算力降 90%，且和"全屏理解"效果差不多
```

### 8.4 双环架构（这是唯一现实的路线）

```
快环（帧级，20~70 ms）    本地小模型 + 规则
  职责：现在能不能打、血够不够、敌人朝哪、按不按
  不需要语言，不需要 LLM，不需要联网

慢环（秒级，3~10 s）      LLM（云端或本地都行）
  职责：这局怎么打、要不要换策略、跟玩家说什么
  它慢没关系 —— 战术本来就该慢，反应靠快环
```

游戏里真实的决策结构就是这样：**手由脊髓管（快环），脑子管目标（慢环）**。
把两者混成"每帧问 LLM"，等于每帧等 1~18 秒，必然不能反应。

### 8.5 单机 / 不联网联机：操作合法性反而简单了

```
单机                 读内存/注入没有封号风险（不联机就不存在反作弊），
                     但仍是"给自己做外挂"的工程量：要适配每个游戏的内存结构
局域网私服（不联网）  同理，没有 VAC/EAC；最稳的是走游戏自带 API（Minecraft 服）
有反作弊的联机游戏    不要做 —— EAC/BattlEye 会直接封
```

推荐顺序（按"合法 + 稳定 + 工作量"）：

```
① 游戏自带 API / 官方模组            Minecraft(Mineflayer)、Factorio、星露谷(SMAPI)
② 回合制/棋牌（自己实现）             状态+动作集合，LLM 直接下，零风险
③ 单机游戏读内存（自己做给自己用）      稳、快，但要逐游戏适配
④ 像素级操作（看屏发键鼠）             最后手段：延迟高、误操作、难调试
```

### 8.6 一句话回答

```
"每帧识别 + 不变化不截图" 能让**感知**跟上帧率（6~18 ms），
但**决策**如果用云端视觉/大模型，就永远跟不上。
要真实时，必须：帧级用本地小模型或游戏 API（20~70 ms 闭环），
秒级才交给 LLM 做战术。
```

### 8.7 如果要做到"AI 真的玩单机动作游戏"，缺的是什么

```
· 一个能在这款游戏上工作的检测模型（敌人/血条/准星）—— 要标注 + 训练
· 一套策略（不是 LLM）：朝敌人 -> 微调准星 -> 开火；或模仿学习
· 按键映射与灵敏度校准（每个游戏不同）
· 一个"卡住检测"（连续 3 秒没进展就重置行为）
```

这三样里，**训练和调参是主要工作量**，接管道（截屏 -> 检测 -> 按键）反而是最简单的部分。
