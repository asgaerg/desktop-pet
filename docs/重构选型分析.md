# 重构为低占用应用的技术选型分析

> 状态：**分析，未执行**。用户要求"功能不变、更小内存和占用，用什么语言写最好"。
> 本文的所有数字都是**实测**（2026 年当前这套 Electron + Python 实现）。

---

## 一、现在的实际占用（基线）

### 内存（私有工作集，实测）

| 进程 | 私有内存 | 说明 |
|---|---|---|
| electron 主进程 | **129.3 MB** | 主进程 + Node |
| electron 渲染进程（宠物） | **109.7 MB** | Chromium 渲染 + 视频解码 + Canvas |
| electron 渲染进程（对话条） | 72.4 MB | 又一份 Chromium 渲染 |
| electron 渲染进程（设置） | 32.6 MB | |
| electron 渲染进程（气泡） | 23.4 MB | |
| electron GPU 进程 | 13.4 MB | |
| **Electron 小计** | **≈ 381 MB** | **6 个进程** |
| python（大脑 sidecar） | **17.8 MB** | 8104 行，纯标准库 + asyncio |
| **合计** | **≈ 400 MB** | |

### 磁盘 / 分发包

| 项 | 大小 |
|---|---|
| Chromium 内核 | ~150 MB+ |
| 立绘素材（107 个 webm） | 51.9 MB |

### 启动耗时

约 **1 秒**才看到立绘（首帧门闸的代价，见进度交接）。

---

## 二、结论先行

**别动 Python 那一侧。只重写"窗口壳"。**

理由是数字很直白：

- Electron 壳占 **381 MB**（95%）
- Python 大脑只占 **17.8 MB**（5%）

就算把 Python 全改成 Rust，最好情况也就从 17.8 MB 降到 3~5 MB —— **省下 13 MB**，
而代价是重写 **8104 行**，外加把 `config/persona.yaml` 的人格逻辑、自主调度、
屏幕理解（PIL / pytesseract）全部搬过去。

**而两侧的边界本来就已经是干净的进程边界**：本地 WebSocket + 版本化协议
（`PROTOCOL_VERSION`，有 11 项协议一致性测试守着）。换掉壳不用碰协议。

所以：**壳换成原生，大脑保持 Python。** 这一步就能拿到 90% 的收益。

---

## 三、推荐方案

### 🥇 首选：Rust + winit + wgpu

| 维度 | 预期 |
|---|---|
| 内存 | **40~70 MB**（vs 400 MB，省 ~85%） |
| 二进制 | **6~15 MB**（vs 150 MB+） |
| 启动 | **50~100 ms**（vs ~1 s） |
| 常驻 CPU | 比现在低（见下面的"渲染管线要改"） |

**为什么是它**：

- 这个应用本质是"**透明窗口 + GPU 合成**"，`wgpu` 直接做逐像素 alpha 合成，
  比浏览器里绕 Canvas 2D 更直接；
- 现在的"抠黑底"（`blackKeyThreshold=25` 的连通性 flood-fill）跑在 **CPU** 上，
  而同样的工作在片元着色器里几乎免费 —— 顺手把 CPU 占用也降下来；
- 跨平台，且没有 GC 停顿（对逐帧动画友好）。

### 🥈 次选：C++ + Win32 + D3D11

内存与 Rust 相当（40~60 MB），Windows 下最"贴金属"。
代价：依赖管理痛苦、内存安全要自己扛、且**锁死 Windows**（现在 Electron 那套是跨平台的）。

### ❌ 不推荐

| 方案 | 为什么不行 |
|---|---|
| Go + Fyne / Wails | 内存能到 80~150 MB，但 **逐像素 alpha 透明做不干净** —— 而"立绘抠黑底 + 真透明窗"是这个应用的命根子 |
| Qt / PySide | 能到 60~120 MB，但 Qt 依赖本身 ~150 MB，**省不下来**；PySide 还要带一个 Python |
| Tauri | 壳薄了、安装包小了，但**运行时仍然跑 WebView2**（Windows 上还是 Chromium 那几个进程），**常驻内存省不了多少**。好处是迁移成本最低（前端代码基本不动） |

> Tauri 值得单独提一句：如果你的痛点其实是"**安装包太大**"而不是"常驻内存"，
> Tauri 是投入产出比最高的选择（复用系统 WebView2）。但按你问的是**内存和占用**，
> 它不解决问题。

## 四、功能不变的最低风险迁移路径

分三步，每步都能独立验证、可回退：

1. **保住协议，换壳** —— 用 Rust 重写 `apps/desktop`，继续跟现有 Python sidecar
   用同一套 WebSocket 协议通信。协议有测试守着，这一步风险最低。
2. **渲染管线搬到 GPU** —— 黑底抠图改写着色器；立绘从 webm 改成
   **帧图集（atlas）+ 或 APNG**（Rust 生态没有现成的 webm 解码，
   而这 107 个素材本来就是序列帧，图集反而更合适）。
3. **逐项补齐窗口行为** —— 透明、穿透、置顶、多显示器、探头旋转。

---

## 五、必须提前知道的硬骨头

这部分是"重写壳"真正的成本，**不是语言问题**：

| # | 问题 | 现状 | 迁移代价 |
|---|---|---|---|
| 1 | **透明窗的平台怪癖** | Chromium 全帮我们处理了（透明背景、`setIgnoreMouseEvents` 转发、DPI） | 各平台要自己踩坑。这是最大的隐性成本 |
| 2 | **视频解码** | Chromium 内置解码 + `drawImage` + `getImageData` | Rust 无现成 webm；建议改图集/APNG |
| 3 | **CJK 字体渲染** | 浏览器自带 | 要捆绑字体文件（+几 MB）并自己做文本排版、换行 |
| 4 | **37 项自动化检查** | `tools/` 下全绿 | **全部要重写** —— 这是本项目最值钱的资产，别低估 |
| 5 | **多窗口编排** | 宠物/对话条/设置/气泡四窗协作、锚点算法 | 每个都要重做，且锚点那套算法（立绘矩形 -> 气泡位置）要再验一遍 |
| 6 | **视频素材 51.9 MB** | webm | 转图集后体积可能**变大**（除非用更好的压缩） |

---

## 六、如果只想"低风险地先降一点"

不改语言也能做的事，按性价比排序：

1. **砍进程数** —— 设置窗、气泡窗按需创建/销毁，而不是常驻。现在四个渲染进程常驻，
   每个 23~110 MB。**这一条可能立省 50~100 MB**，改动量最小。
2. **合并对话条和气泡**成一个窗口（都是"宠物旁边的浮层"）。
3. **给 Electron 加内存相关开关**（进程回收、堆上限），效果有限但零风险。
4. **立绘素材转更省的编码**（降低分辨率或用 AV1），影响的是磁盘和显存。

> 我的建议：**先做第 1 条**。如果降下来还嫌大，再考虑 Rust 重写壳。

---

## 七、一句话回答

> **壳用 Rust（winit + wgpu）；大脑保持 Python 不动。**
> 预期从 ~400 MB 降到 40~70 MB、安装包从 150 MB+ 降到 10 MB 级、启动从 ~1s 降到 ~0.1s。
> 但真正的成本不在语言，而在**重建 37 项自动化检查**与**自己处理透明窗的平台差异**。

## 八、修正：参考包的实测结论（推翻本文第三节的 Qt 判断）

用户指出参考应用 `dsh-pet-standalone-webm-chat.zip`「功能比我们多，安装包却很小」。
**实测后它并不小**，但这次实测**推翻了我上面的 Qt 结论**：

| | 参考包 | 我们的（打包后估算） |
|---|---|---|
| 压缩包 / 安装器 | **153.8 MB** | — |
| 解压后 | **274.2 MB**（1168 项） | **≈ 369 MB** |
| 运行时 | PyInstaller + Python 3.11 + **PySide6(Qt)** | Electron(Chromium) |
| 运行时占用 | Qt 相关 **67.4 MB** | Electron dist **265.3 MB** |
| 最大单项 | `ffmpeg.exe` **83.6 MB** | — |
| 立绘解码 | **自带 ffmpeg**（84 MB 就为解 webm） | Chromium 内置，**0 额外体积** |
| 素材 | 嵌入包内 | 214 个 webm / 103.8 MB |

### 结论修正

- 我上面写「Qt 依赖本身 ~150 MB，省不下来」——**是错的，实测 67.4 MB**。
- 所以 **PySide6 这条路是真实可行且更省的**：一个 1168 项依赖的应用跑得起来，
  而 Qt 那层只有 Electron 的 **1/4**。
- 参考包"看起来小"是因为它是**装好的干净目录**，而我们看到的是**开发树**
  （`node_modules` 303 MB + `.test-build` 57.5 MB）。

修正后的选型：

| 方案 | 打包后磁盘 | 内存（估计） | 备注 |
|---|---|---|---|
| 现状 Electron | ~369 MB | **~400 MB**（实测） | |
| **PySide6 + Python** | **~170 MB** | ~100–200 MB | 参考包走的就是这条；**大脑可直接复用，不用跨进程** |
| Rust + wgpu | **~60 MB** | 40–70 MB | 最省，但要重建 37 项测试 |

> **PySide6 值得重新考虑**：它能把"大脑"（已经是 Python）和"壳"合并成一种语言，
> 省掉跨进程 WebSocket，还能用 Qt 原生解码 —— **不必背那 84 MB 的 ffmpeg**。

## ⭐ 决定（已定）

**采用 PySide6 + Python 重构。语音功能暂缓，先做重构本身。**

理由（按权重）：

1. **大脑本来就是 Python**（8104 行，纯标准库 + asyncio）—— 合并成一种语言，
   省掉跨进程 WebSocket 与协议维护成本；
2. **磁盘/内存都有实测背书**：参考包 `dsh-pet-standalone-webm-chat.zip` 证明
   Qt 那一层只占 **67.4 MB**（Electron 是 265.3 MB），内存预计从 ~400 MB 降到 ~100–200 MB；
3. **为后续语音铺路**：采集 / VAD / ASR / TTS / 大脑能落在同一种语言里，
   而 `voice.py`（1132 行）已经写好，将来只需接线（详见第九节）；
4. Rust 虽然最省（~60 MB / 40–70 MB 内存），但要重建 37 项自动化检查、
   自己写音频线程与重采样 —— 对"近期要上语音"的路线不划算。

**施工顺序建议**（下一步从这里挑）：

1. 先把 `apps/brain/pet/*.py` 原样**作为库**跑起来（它已经无第三方依赖），
   验证 `python -m pet.selftest` 那 58 项在 PySide6 壳里同样过；
2. 再逐窗替换壳：宠物窗 → 气泡窗 → 对话条 → 设置窗
   （每个窗口都能独立验证，可回退）；
3. 渲染管线搬到 Qt：黑底抠图改 `QImage` 处理或 shader，立绘从 webm 改成
   **帧图集 / APNG**（Qt 不带 webm 解码，而素材本来就是序列帧）；
4. 重建测试门禁 —— **这是最大的工作量，别低估**（现有 37 项检查是本项目最值钱的资产）。

⚠️ 已知不必再走一遍的弯路：**不要背 ffmpeg**。参考包为解 webm 带了 83.6 MB 的
`ffmpeg.exe`，而素材是序列帧，转图集后既省体积又省一个进程。

## 九、实时语音交流：可行性

### 好消息：**骨架已经写完了，缺的只是"接线"**

| 层 | 现状 |
|---|---|
| `apps/brain/pet/voice.py` | **1132 行**，已实现：`AudioFrame` / `VoiceActivityDetector` / `Endpointer`（说完判定）/ `Utterance` / `Transcript` / **插话打断**（`barge_in_frames`）/ `OpenAIAsrEngine` / `OpenAITtsEngine` / `VoicePipeline` |
| 协议 | `voice.state` / `voice.audio` / `user.voice` / `voice.control` 全部定义好，且**音频本体走二进制帧**（`AudioPairer` 负责序号配对） |
| 配置位 | `config/persona.yaml` 的 `providers.asr` / `providers.tts`，含 `end_silence_ms: 500`、`allow_barge_in: true` |
| 渲染层采集 | `voice-io.js` 有 `getUserMedia` + `ScriptProcessorNode` → 16k PCM 帧 |
| 播放 | `VoiceIO` 已负责解码、打断上一段、同时只播一段 |

### 缺的三件事

1. **麦克风开关的 UI**（关键）
   - `VoiceIO` 在 `app.js` 里**只为播放创建**（`if (!audio) audio = new VoiceIO()`）；
   - 它自带的**采集能力没有任何调用方** —— 因为之前那轮把宠物界面上的语音按钮删掉了。
   - 所以现在"开麦"没有入口。补一个按钮/快捷键即可。

2. **上行音频帧真的发给 brain** —— 需要确认 `voice.control {enabled:true}` 之后
   PCM 帧确实以二进制帧上行（下行有 `pet:voice-audio`，上行要对称）。

3. **ASR / TTS 换一个真正有音频接口的服务商**（⚠️ 见下）

### ⚠️ 配置里的坑：**DeepSeek 没有语音接口**

`persona.yaml` 里：

```yaml
asr:
  base_url: ""               # 留空则复用 providers.brain.base_url
  api_key_env: DEEPSEEK_API_KEY
```

`base_url` 留空会复用到 `https://api.deepseek.com/v1`，而 **DeepSeek 只提供文本
接口，没有 `/audio/transcriptions` 或 `/audio/speech`** —— 照现在这样填，调用会失败。

可选路线（按省心程度）：

| 路线 | 说明 |
|---|---|
| 本地 Whisper（`provider: local`） | 配置里已支持，未安装时自动降级为 mock。**隐私最好、零 API 成本**，但要装 `faster-whisper` |
| OpenAI 兼容第三方 | 豆包/火山、阿里、讯飞等大多有，需要一层 OpenAI 兼容代理（社区有现成的，如 [doubao-asr2-openai-proxy](https://github.com/gydx6/doubao-asr2-openai-proxy)） |
| OpenAI 官方 | 最省心，国内访问需代理 |

> `api_key_env` 也不该叫 `DEEPSEEK_API_KEY` —— 它指的是语音服务的密钥，
> 名字会误导人（以为语音也走 DeepSeek）。

### 延迟预算（决定"像不像在聊天"）

```
用户说完 --end_silence_ms(500ms)--> ASR --> LLM --> TTS --> 播放
```

| 环节 | 云端全链 | 本地 Whisper |
|---|---|---|
| 说完判定 | 500 ms（可调，最影响手感） | 同 |
| ASR | 300–800 ms | 200–600 ms（看模型大小） |
| LLM 首字 | 300–700 ms（DeepSeek 流式） | 同 |
| TTS 首块 | 300–600 ms | 100–300 ms（本地） |
| **合计到出声** | **≈ 1.5–2.6 s** | **≈ 1.1–2.0 s** |

**可以压到 1 秒出头**的两个关键优化（都要代码改动）：

1. **ASR 出 partial 就先把文字喂给 LLM**（`user.voice` 已带 `final?: boolean` 字段，
   协议已经为流式识别留好了位置）—— 省下"等说完"的 500ms。
2. **LLM 边出 token 边分句喂 TTS**，而不是等整段生成完 —— 省下整段生成时间。

### 这件事**不影响**语言选型

语音链路的瓶颈在**网络 I/O**，不在 CPU：

- 本地 Whisper 若要跑，就是个进程（Python 生态最顺，`faster-whisper` 现成）；
- 音频采集在任何语言里都是平台 API 包装（原生下是 WASAPI / `cpal`）；
- **唯一受选型影响的**：现在用浏览器 `ScriptProcessorNode` 采集，
  换原生要自己写音频线程与重采样。而 `ScriptProcessorNode` 已废弃
  （虽然 Chromium 上仍可用）。

**所以**：如果你打算**近期**上语音，那"**PySide6 + Python**"这条路的性价比最高 ——
采集、VAD、ASR、TTS、大脑都在同一种语言里，不用维护跨进程协议；
而它对内存的收益也已经有参考包实测背书（Qt 67 MB vs Electron 265 MB）。
