# 开发约定

> 这份文件不长，但**每次动手前都该看一眼**。它定的是"什么时候提交、什么时候发版"。

## 一、提交规矩（2026-10-19 用户定的）

> 用户原话：「你现在每次改完都在提交吧，不用这样，我定个规矩，这个项目每次打包之前才进行更新仓库，每次更新按版本来。」

**平时改代码：只落文件，不 `git commit`、不 `git push`。**

- 改完直接停下，让用户在本地试。
- 工作区里堆着一堆未提交的改动是**正常状态**，不是"忘了提交"。
- 想看改了什么：`git status` / `git diff`，不需要先提交。

**只有每次打包发版之前，才统一提交一次。**

这条规矩的理由（写给以后的人）：
- 这个阶段改得快，一个功能经常改十几次；每次提交会产出大量"修一半"的历史，回滚时反而看不清。
- 用户是**本地试**而不是看 CI —— 提交对他没有价值，只会让仓库历史变脏。
- 按版本提交，`git log` 就是一份干净的版本清单，出问题能直接定位到"哪个版本引入的"。

## 二、发版流程（打包前照着做）

```powershell
# 1) 改版本号（四处一起改：根 / desktop / protocol / pet）
python tools/bump-version.py 0.1.1

# 2) 写这一版的发布说明
#    docs/RELEASE-v0.1.1.md  —— 内容照 docs/RELEASE-v0.1.0.md 的结构

# 3) 跑测试（两个都要绿）
cd apps/desktop; npm test
cd apps/brain;   python -m pet.selftest

# 4) 提交 + 打标签（**这时候才提交**）
git add -A
git commit -m "release: v0.1.1"
git tag v0.1.1
git push origin main --tags

# 5) 打包
cd apps/desktop; npm run package:online

# 6) 上传 GitHub Release
#    见 docs/打包说明.md（上传走 curl --noproxy '*'，见那里的说明）
```

## 三、版本号怎么定

三段式 `主.次.修`：

| 情况 | 例子 |
|---|---|
| 修 bug、小改动 | `0.1.0` -> `0.1.1` |
| 加了新功能（用户能感知） | `0.1.1` -> `0.2.0` |
| 大改结构 / 不兼容 | `0.x` -> `1.0.0` |

⚠️ 版本号只在**打包前**改，不要平时随手动 —— 它和"这一版实际发了什么"必须对得上。

## 四、哪些东西绝对不进仓库

- 密钥、凭据（`credentials.json`、任何 `api_key`）
- 用户数据（`pet-data/`、`memory/`、聊天记录、截图）
- 模型权重（`models/`、`asr-models/`）
- 构建产物（`release*/`、`dist/`、`node_modules/`、`.venv/`）

细节见 `.gitignore` 与 `README.md` 的「API 与隐私」一节。

## 五、改完代码后最少跑什么

不是每次都要跑完整的 `npm test`（它要一两分钟），但这几项在**打包前必须有**：

```
cd apps/desktop
npm run check:types        # TS 类型
npm run check:renderer     # 渲染层语法（这次就是它没跑，才把 app.js 改坏了）
npm run test:main          # 主进程 461 项
cd apps/brain
python -m pet.selftest     # Python 115 项
```

> 2026-10-19 的教训：改完 `app.js` 直接提交、没跑 `check:renderer`，
> 结果一行模板字符串被写坏，宠物立绘整页不显示 —— 用户看到的是"它不见了"。
> **改渲染层必须跑 `check:renderer`。**
